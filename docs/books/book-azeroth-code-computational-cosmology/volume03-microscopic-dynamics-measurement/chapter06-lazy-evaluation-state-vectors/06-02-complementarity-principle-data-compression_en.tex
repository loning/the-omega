\section{Textures vs Models (Complementarity Principle and Data Compression)}

\textit{(Textures vs Models - Complementarity Principle and Data Compression)}

\begin{quote}
\textbf{``Waves and particles are not two properties of matter, but two formats of the same data. Like game files are compressed packages (waves) on hard drive, but decompressed files (particles) in running memory. The universe dynamically switches data formats based on whether you want to `transmit' or `interact'.''}
\end{quote}

In section 6.1, we discussed that Heisenberg's principle is resolution limitation. This leads to another big question: \textbf{Wave-particle duality}.

Why does light sometimes act like waves, sometimes like particles?
In \textbf{Code of Azeroth}, this is not mysterious; this is \textbf{dynamic data compression strategy}.

\subsection{Format Conversion: Bitmap vs Vector Graphics}

At the code level, waves and particles are just two \textbf{representations} of data.

\begin{enumerate}
\item \textbf{Particle view (bitmap/entity)}:
\begin{itemize}
\item Information is \textbf{localized} (at this coordinate point).
\item Suitable for \textbf{collision, pickup, combat}.
\item This is the BOSS you see in instances that can be fought.
\end{itemize}

\item \textbf{Wave view (spectrum/compressed package)}:
\begin{itemize}
\item Information is \textbf{dispersed} (everywhere).
\item Suitable for \textbf{propagation, loading, cutscenes}.
\item This is the BOSS data packet in ``may appear'' state.
\end{itemize}
\end{enumerate}

\textbf{Mathematical essence}:
Converting from particle to wave is doing a \textbf{format conversion (ZIP compression)}.
The so-called complementarity principle means you cannot keep a file simultaneously in ``compressed'' and ``decompressed'' states.

\subsection{Compress When Transmitting, Decompress When Interacting}

Why does the universe bother with these two formats? To \textbf{save bandwidth}.

\textbf{Scenario one: Running across map (free propagation)}
\begin{itemize}
\item \textbf{Task}: A fireball flies from your hand to the monster's face.
\item \textbf{Particle mode (dumb method)}: If using particle mode, the server must calculate its position at every pixel every frame to prevent clipping. This is exhausting.
\item \textbf{Wave mode (smart method)}: If using wave mode, it's just a mathematical formula (phase rotation). Extremely simple to calculate.
\item \textbf{Conclusion}: \textbf{Wave is the most efficient transmission format}. As long as nothing hits, the system defaults to packing all flying things as waves (compressed packages), greatly reducing computation.
\end{itemize}

\textbf{Scenario two: Hit (local interaction)}
\begin{itemize}
\item \textbf{Task}: Fireball hits the face.
\item \textbf{Wave mode (dumb method)}: Waves are spread out; can't calculate specific damage judgment point.
\item \textbf{Particle mode (smart method)}: System needs to know precise coordinates $(\text{x}, \text{y}, \text{z})$ to deduct health.
\item \textbf{Conclusion}: \textbf{Particle is the most efficient interaction format}. When collision occurs, the system must \textbf{decompress} the wave back to particle, execute collision detection. This is physics' \textbf{``collapse''}.
\end{itemize}

\subsection{Observer's Choice: Double-Slit Experiment}

When you do the double-slit interference experiment, you're actually configuring a \textbf{decoder} as a player.

\begin{itemize}
\item \textbf{No detector}: You tell the server: ``I don't care which path it takes.'' Server thinks: ``Great, saves trouble.'' So it maintains \textbf{wave encoding} (compressed package mode), passes through double slits, draws interference fringes on screen.
\item \textbf{Place detector}: You tell the server: ``I want to see its precise path.'' Server is forced to execute \texttt{Unzip()}, decompress data back to \textbf{particle encoding}. After becoming particle, it can only pass through one slit; interference fringes disappear.
\end{itemize}

\textbf{Theorem 6.2.1 (What You See Is What You Ask For)}

Reality appears as what (wave or particle) depends on what format you ask the system for.
\[
\text{reality} = \text{data} + \text{your request}
\]

\subsection{Delayed Choice: Render on Demand}

Wheeler's \textbf{delayed choice experiment} proved that even if photons have already flown over, as long as you haven't looked at the result, you can still change its past.

This is too normal from a code perspective: This is \textbf{lazy evaluation}.

\begin{itemize}
\item Photons remain \textbf{compressed packages} during flight.
\item \textbf{Log} hasn't been generated yet.
\item Only at the last moment when you decide how to look at it does the system \textbf{generate on-the-fly} its historical trajectory based on your decision.
\end{itemize}

This is like \textbf{frustum culling} in games: Graphics cards always only render the instant you're looking at.

\subsection{Summary: The Coding of Reality}

The complementarity principle reveals a core optimization technique of the universe operating system: \textbf{dynamic transcoding}.

\begin{enumerate}
\item \textbf{Vacuum is frequency domain}: To save bandwidth, empty places are all waves.
\item \textbf{Matter is time domain}: To calculate collisions, populated places are all particles.
\item \textbf{Observation is decoding}: Your eyes determine the data decompression method.
\end{enumerate}

The wave-particle debate physicists argued for a hundred years actually confused \textbf{source files} with \textbf{display formats}. The universe has only one thing---quantum information flow---which switches between compression and decompression as needed.

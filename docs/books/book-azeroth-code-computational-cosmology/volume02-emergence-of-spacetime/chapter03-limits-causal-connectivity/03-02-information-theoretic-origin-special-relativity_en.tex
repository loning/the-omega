\subsection{Reference Frame: The Data Stream You See}

In distributed systems theory, there is no such thing as ``global unified time.''

Each player's client has its own local clock.

\textbf{Definition 3.2.1 (Physical Reference Frame)}

A \textbf{reference frame} is essentially a \textbf{sorting protocol}. It's responsible for arranging various out-of-order data packets you receive (explosions here, shouts there) into a ``story'' with sequential order.

\begin{itemize}
\item \textbf{Rest frame}: You looking at yourself. No latency, instant response.
\item \textbf{Moving frame}: You looking at a rogue running around. His data packets take time to arrive.
\end{itemize}

Due to data transmission delay (light speed limit), when you try to lock onto a fast-moving target, the system must perform \textbf{interpolation compensation}. If this compensation algorithm is to ensure causal logic doesn't go wrong (like can't see him fall before my fireball hits), then \textbf{Lorentz transformation} is the only legal algorithm.

\subsection{Resource Competition and Time Dilation: CPU Can't Keep Up}

Special relativity's most famous prediction is: Moving clocks run slow.

In computational cosmology, this is actually due to \textbf{resource contention}.

According to Volume I's theorem, every physical object (like that rogue) has an upper limit on information it can process per unit time (limited by Planck frequency). This ``computational budget'' must be divided between two things:

\begin{enumerate}
\item \textbf{Processing position updates ($v_{ext}$)}: Calculating his displacement on the map. This is GPU-intensive.
\item \textbf{Processing internal logic ($v_{int}$)}: Calculating his health regeneration, energy recovery, or his watch ticking.
\end{enumerate}

\textbf{Theorem 3.2.1 (Computational Conservation Theorem / Pythagorean Theorem)}

For any unit, his external movement speed and internal refresh speed must satisfy:

\[
v_{ext}^2 + v_{int}^2 = c^2
\]

\textbf{In plain language}: The server allocates fixed resources to each unit.

\begin{itemize}
\item If you \textbf{stand still} ($v_{ext}=0$), all resources are used to refresh your internal state; your time passes fastest ($v_{int}=c$).
\item If you \textbf{run very fast} ($v_{ext}$ is large), the server must use most computing power to calculate your coordinate changes. So, the computing power allocated to process ``aging'' or ``health regeneration'' decreases.
\end{itemize}

\textbf{This is the truth of time dilation}: The reason you see people in spaceships moving slowly is not because time is doing magic, but because their system is busy processing the high-priority task of ``movement,'' causing the thread processing ``internal logic'' to be forcibly downclocked.

This is \textbf{system-level lag}.

\subsection{Length Contraction: Lowering Quality for Smoothness}

Length contraction is usually misunderstood as objects actually being flattened. From an information theory perspective, this is actually \textbf{downsampling}.

When you measure a speeding mage's height, you're actually requesting the server to simultaneously return coordinates of his head and feet.

But with limited bandwidth, to ensure you receive complete data packets within a finite time window, the system must \textbf{compress} the data.

\[
L' = L \sqrt{1 - \frac{v^2}{c^2}}
\]

This is like watching online video. If network speed isn't enough (limited by $c$), to keep video smooth (time continuous), the system automatically lowers image resolution (spatial contraction).

So-called length contraction is \textbf{sacrificing resolution for frame rate}.

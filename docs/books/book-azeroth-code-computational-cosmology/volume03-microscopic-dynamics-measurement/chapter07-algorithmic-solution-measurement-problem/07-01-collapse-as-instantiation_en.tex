\subsection{Type Error: Class vs Object}

In old physics, everyone treated wave functions and particles as the same thing. This is a \textbf{type error}.

\begin{enumerate}
\item \textbf{Wave function is code (Class)}:
\begin{itemize}
\item It describes what might happen (drop rate table, attribute ranges).
\item It doesn't occupy memory; it's just rules.
\item Example: \texttt{Creature\_Tiger} (a tiger design blueprint).
\end{itemize}

\item \textbf{Particle is instance (Object)}:
\begin{itemize}
\item It's concrete, unique entity.
\item It occupies specific coordinates, has specific health.
\item Example: \texttt{Guid\_10086} (that specific tiger in Stranglethorn Vale).
\end{itemize}
\end{enumerate}

\textbf{Conclusion}:
Wave function and particle are two different states of the same logical entity. The transformation between them (measurement) is the system executing a \textbf{constructor}.

\subsection{Who Triggers the Constructor?}

Since the world is originally code (wave), why does it become entity (particle)?
Answer: \textbf{Interaction request}.

When an electron interacts with macroscopic environment (like your retina, or Stormwind's city wall), the macroscopic environment---as a complex system---sends an \textbf{attribute query} to the electron.

\begin{itemize}
\item \textbf{Query}: \texttt{Tiger.getPosition()} (Where is the tiger?)
\item \textbf{System response}:
\begin{enumerate}
\item Detects tiger is in uninstantiated superposition state (in grass, maybe left or right).
\item Calls \textbf{random number generator (RNG)}, draws a number according to probability distribution.
\item \textbf{Runs constructor}: \texttt{new Tiger(x, y)}.
\item \textbf{Allocates video memory}: Renders a tiger at coordinates $(x, y)$.
\item \textbf{Returns result}: You see the tiger there.
\end{enumerate}
\end{itemize}

To the observer, the wave function instantly contracts to that point. But at the system bottom layer, this is just \textbf{generating specific values from probability table}.

Modern game engines widely use \textbf{Just-In-Time Compilation (JIT)} technology: Resources are only loaded when they're about to enter player's view.

\textbf{Theorem 7.1.1 (JIT Reality Theorem)}

To save resources, physical systems only generate definite entities at \textbf{interaction interfaces}. In unobserved places (unloaded maps), physical reality remains in \textbf{intermediate code (wave function)} state.

This explains why we can't find hidden variables.
Hidden variable theory believes: The tiger's position was already determined before discovery.
Computational theory believes: \textbf{Before discovery, the tiger's position attribute wasn't allocated memory at all.} Trying to ask ``where was it before discovery'' is like trying to read a null pointer.

\subsection{Object-Oriented Explanation of Schrödinger's Cat}

Now we can perfectly solve \textbf{Schrödinger's cat}.

The cat in the box is a \textbf{closure} or \textbf{lazy object}.
The system records: \texttt{State = Depend\_on(Poison) -> Depend\_on(Atom)}.

At this point, the cat doesn't have ``dead'' or ``alive'' attributes because it hasn't been \textbf{evaluated} yet. It's just a \textbf{function waiting to be executed}.

When you open the box (perform observation):
\begin{enumerate}
\item You trigger \textbf{forced evaluation}.
\item System traces causal chain, throws dice to determine if atom decays.
\item Based on result, \textbf{instantly instantiates} a dead or alive cat model.
\end{enumerate}

The cat never was in ``both dead and alive'' state; it was just in \textbf{``waiting to load''} state.
